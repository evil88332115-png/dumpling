### 8.8 Vulnerability status (VEX) and release gate

Each row of section 8 is a candidate vulnerability found by automated matching of the SBOM components against vulnerability data, not by itself a known exploitable vulnerability. A VEX (Vulnerability Exploitability eXchange) statement records, per row, whether the product is affected and why. Statements come from, in this order: (1) decisions recorded by people – the analysis in Dependency-Track and the project's annotation file `CRA/Config/vex-annotations.json` (carried to later releases automatically); (2) the distribution's own records for rows reported only via NVD/GitHub (`resolved`: the installed package contains the backported fix); (3) the kernel configuration check (`not_affected`, `code_not_present`: the vulnerable code is not built); (4) NVIDIA bulletins that do not name this release line but predate it (`in_triage` – presumed, never `not_affected`); (5) the project's bulk rules `CRA/Config/vex-rules.json` (evidence rules, which set `not_affected` only from the product's artifacts – kernel configuration, kernel modules, Ubuntu CVE Tracker status – and triage rules, which set only `exploitable` (a response is optional), or `in_triage`; only for rows without a decision from (1)–(4); never for rows in a KEV catalogue; each such statement names its rule). The first source with a decision is used; a different decision from a later source is listed as a conflict and does not override it. Rows without any decision are `untriaged`. They are written to the VEX files as well, as `in_triage` in CycloneDX (`under_investigation` in OpenVEX) with the property `dumpling:assessment` = `NOT_ASSESSED` (OpenVEX: status notes "dumpling: not assessed"). Such a statement means that the row has not been assessed; it does not mean that anyone is investigating it. The release gate counts these rows as `untriaged`, not as `in_triage`, and they are not written back to Dependency-Track. Every `resolved` or `not_affected` statement (an exclusion) also records the type and location of its evidence (D-035): in CycloneDX the properties `dumpling:evidence`, `dumpling:evidence-location` and, for a specific kernel, `dumpling:evidence-kernel`; in OpenVEX one line `dumpling: evidence=<type>; location=<location>` per piece of evidence in the status notes. The files for customers carry the type only, as a fixed sentence (`Evidence: …`), never the location.
